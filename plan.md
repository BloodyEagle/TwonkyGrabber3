# План: Twonky Grabber (агентский режим)
## 0. Контекст для агента

Приложение ищет и скачивает медиафайлы (только изображения и видео) с Twonky-серверов. Файл адресуется номером: {base}/disk/O0$2$20I<n>. Стартовый номер 5000. Нумерация бывает двух видов (зависит от прошивки): подряд (шаг 1) или с шагом 256; в одном 256-блоке может быть несколько файлов. Превью: ?scale=WxH в конце URL (размер приблизительный, пропорции сохраняются). Архитектура: Angular-клиент + Express-сервер, оба на TypeScript; сервер скачивает файлы себе на диск (не в браузер), в проде раздаёт собранный фронт с того же порта.

Критические ограничения:

     Из браузера к Twonky напрямую нельзя (CORS) — весь трафик идёт через Express-прокси.
     Часто просроченный TLS-сертификат — все исходящие запросы с rejectUnauthorized: false.
     На старых прошивках HEAD не работает — fallback: GET с Range: bytes=0-0.
     404 = «файла нет» (не ошибка); таймаут/обрыв = «неизвестно» (ретраи, при серии — пауза).

## 1. Стек и соглашения

   Node ≥ 20, TypeScript 5 strict, без any (осознанные исключения — с комментарием). Сервер: CommonJS, dev через tsx watch, prod — сборка tsc + node. Express 4 (не 5).
   Angular 18+: standalone-компоненты, signals, OnPush, SCSS. Без NgRx и UI-библиотек — компактные собственные стили, тексты интерфейса на русском.
   Зависимости сервера: express + @types/* + typescript, tsx (dev). Никаких axios/fetch-обёрток — только встроенные http/https (контроль TLS и таймаутов).
   Все числовые параметры — в server/src/config.ts. Магические числа в коде запрещены.
   Зависимости из браузера к Twonky нет вообще: картинки, превью, проверки — только через /api.

## 5. Сканер — спецификация

   1. Подключение. Парсинг URL: протокол (default http), порт (default 9000 для http / 443 для https), путь (default /disk/), префикс O0$2$20I (парсится из хвоста, если указан), номер (из хвоста, иначе 5000). Проверка доступности: один probe на стартовый номер — любой HTTP-ответ (в т.ч. 404) = сервер доступен.
   2. Разведка. HEAD на start..start+255. Считаем существующие image/video. Ноль ответов → error. Найдено ≥128 → режим seq; иначе delta, якоря = найденные номера (обычно 1–7); ноль найдено → виртуальный якорь на старте.
   3. Руки. seq: вперёд от start+256 (шаг 1), назад от start-1 (шаг 1), назад — до 0 включительно. delta: от каждого якоря две руки ±256. Руки делят общий семафор; глобальный visited-сет исключает повторные пробы и дубли.
   4. Секанье. Рука планирует батчи по PROBE_BATCH позиций. Промах → missStreak++. missStreak ≥ 500: если jumpsDone < 5 → прыжок dir × 1000 × step, jumpsDone++; иначе фаза sparse.
   5. Sparse. 100 проб, шаг random 1000–10000; в delta-режиме шаг округлять кратно 256 (иначе проба всегда «мимо» сетки). Все промахи → рука stopped (конец библиотеки в эту сторону).
   6. Находка после прыжка/sparse → фаза gapfill: идти в обратном направлении с шагом руки до 500 подряд промахов / visited-позиции / границы; затем продолжить обычный скан от находка + step×dir.
   7. Плотные проходы. У каждой руки свой счётчик foundSinceSweep; при 2000 — поставить в очередь 256 подряд идущих номеров с шагом 1 (вперёд: от находки; назад: от находки−255), пропуская visited.
   8. Пробы. HEAD → при 405/501 GET c Range: bytes=0-0 (206/200 = есть). Существует + content-type image/* или video/* → файл найден; прочее — промах (логировать). Сетевая ошибка: 2 ретрая (задержки 400/800 мс), 12 подряд на уровне сканера → paused + reason (пользователь возобновляет вручную).
   9. Завершение: все руки stopped → done. Остановка/пауза/резюм; reset очищает всё.
   10. Персистентность: connection, status, mode, probed, arms, found (сортировка по номеру, дедуп по номеру). visited не сохранять (допустимы повторные пробы после рестарта). При загрузке: scanning→paused + флаг wasRunning → автопродолжение при старте сервера. Состояние найденных файлов менять нельзя — фронт опирается на номер.

## 6. Загрузчик — спецификация

   Очередь — элементы по номеру (дедуп при добавлении). «Скачать всё»: autoAll=true + поставить все текущие найденные; дальше SSE found → автодобавление.
   Пул воркеров: старт 4. Авто-режим: каждые 5 с считается скорость (байт за интервал) и скорость на активный поток; ≥1 МБ/с и есть ожидающие → target+1 (строго по одному, не прыжком), ≤150 КБ/с (при ненулевом трафике) или >2 отказов за интервал → target−1; пределы 1..32. Ручной режим: слайдер. Лишние воркеры выходят после завершения текущего файла.
   Файл: свежий HEAD (размер, тип) → имя = полный хвост URL + расширение из content-type (карта mime→ext, unknown → bin). Дубликаты: файл с тем же именем и тем же размером → skipped («уже скачан»); размер отличается → _1, _2… до первого свободного. Скачивание в <имя>.part с докачкой (Range: bytes=N-; 206 → дописывать, 200 → с нуля), сверка итогового размера, rename. Ретраи: 2. Пауза/резюм, удаление pending/failed, retry-failed, clear-completed, reset.
   Персистентность: items (active→pending при загрузке), threadsMode/Manual/Target, autoAll, paused; очередь возобновляется при старте.

## 7. Превью-прокси

GET /api/thumb?n=<номер>&w=<W>&h=<H>: запросить ?scale=WxH; если не 200 — оригинал, но отдать только если content-type image/* (видео в <img> показать нельзя → 404, фронт ставит заглушку). &orig=1 — принудительно оригинал (для клика «открыть полное»). w/h клампить 16..2000. Заголовки: Content-Type/Length от апстрима, Cache-Control: public, max-age=86400 (URL различаются по w/h — кэш браузера корректен). Обрыв клиента → destroy апстрима.

## 8. API-контракт

| Метод/путь | Тело/параметры | Ответ |
|---|---|---|
| GET /api/health | — | `{ok}` |
| POST /api/connect | `{url}` | `{ok, connection, exists}`; 409 если скан идёт; 502 если недоступен |
| POST /api/scan/start, /api/scan/stop | — | `{ok, status, reason}` |
| GET /api/scan/status | — | ScanProgress |
| GET /api/files | page,size,sort=asc\|desc,type=all\|image\|video | `{total,page,size,items}` |
| GET /api/thumb | n,w,h[,orig=1] | картинка или 404 |
| POST /api/queue | `{numbers:[]}` | `{ok, added}` |
| POST /api/queue/all | — | `{ok, added}` (включает autoAll) |
| POST /api/queue/pause, /resume, /retry-failed, /clear-completed | — | `{ok}` |
| DELETE /api/queue/:number | — | `{ok}` |
| GET /api/queue | page,size | QueueState + items |
| GET/POST /api/settings | `{threadsMode, threadsValue, autoAll}` | settings |
| POST /api/state/reset | `{scan=true, queue=true}` | `{ok}` (скачанные файлы не трогать) |
| GET /api/events | SSE | события `scan`, `found`, `queue` |

SSE: scan ~раз в 500 мс, found — батчами (буфер, флеш ~500 мс), queue ~раз в 1 с; heartbeat-комментарий раз в 15 с; при подключении сразу слать снимок (scan + queue). EventSource переподключается сам.

# 11. Definition of Done (ручные сценарии)

1. Неверный адрес → понятная ошибка; верный → connected.
2. Скан идёт, счётчики растут; пауза по кнопке и по недоступности сервера; резюм.
3. Пагинация, фильтры, сортировка; «новые файлы» после находок назад.
4. Выбор + Shift-диапазон → очередь → файлы в DOWNLOAD_DIR, имена O0$2$20I<n>.<ext>; повтор → skip; файл другого размера рядом → _1.
5. «Скачать всё» автоподхватывает новые находки до конца скана.
6. Потоки: рост постепенный (по одному за 5 с) на быстром сервере, падение на медленном.
7. Все 4 размера превью; оранжевый значок на полноразмерных; заглушка на видео без превью.
8. Рестарт: скан и очередь продолжаются с места.
9. Сброс состояния очищает списки, файлы на диске остаются.
10. https с просроченным сертификатом: поиск и скачивание работают.
11. ни одного элемента вне палитры токенов.
12. пустое/загрузка/ошибка-состояния реализованы.
13. оранжевый значок виден и с тултипом.
14. панель очереди — бейдж активных в шапке, drawer работает на узком экране.

## 13. Дизайн и UX (тёмная тема)

### 13.1 Принципы

- Единственная тема — тёмная, фиксированная. Переключатель тем не делаем (объём не оправдан).
- Интуитивность = видимый путь действия: Подключить → Начать скан → галерея → выбор → в очередь → скачивание. На каждом шаге доступная следующая кнопка активна, недоступная — приглушена с тултипом «почему» (например: «Сначала подключитесь к серверу»).
- Важные состояния всегда на виду: статус скана и счётчики — в закреплённой панели; «Выбрано N» + кнопка «В очередь» подсвечены, пока есть выбор; панель очереди доступна из шапки с бейджем активных загрузок.
- Никаких действий «вслепую»: деструктивное (сброс, очистка) — только через подтверждение; результат действий (добавлено N, ошибка) — тостом.
- Текст — русский, глаголы консистентны: Подключить / Начать / Остановить / Продолжить / В очередь / Скачать всё. Числа с разрядами (12 345), размеры — человекочитаемые (КБ/МБ/ГБ), скорость — МБ/с. Технические показатели (eps, target потоков) — с тултипами.

### Bugs → план исправлений

#### 1. Скан останавливается, не дойдя до всех видео (пп. 1 и 3 — одна причина)

Причина. Досрочная остановка идёт не из `checkStatsDone` (там корректно суммарный счётчик),
а из `checkDone()` (`scanner.ts:739`): `arms.every(stopped)` → `status='done'`, `reason=null`.
Рука уходит в `stopped` не «библиотека кончилась», а «алгоритм сдался»: `MISS_LIMIT=500` промахов
→ 5 прыжков → `sparse` после `SPARSE_PROBES=100` промахов → `stopped` (`scanner.ts:492-514`).
`checkDone` не сверяется со `serverTotals`, а `reason=null` скрывает причину.

Усугубляет:
- режим выбирается глобально по разведке 256 номеров (`scanner.ts:413`, seq vs delta), а нумерация
  Twonky часто смешанная (фото подряд, видео с шагом 256) — один режим не покрывает оба вида;
- `enqueueSweep` (`scanner.ts:704`) покрывает 256 номеров только в одну сторону от находки
  (`dir=1`: `[n, n+255]`, `dir=-1`: `[n-255, n]`), а не симметрично вокруг;
- крупные «дыры» (удалённые файлы) заставляют scan-руку сдаться до остальных файлов.

Как исправить:
1. Разделить `covered` (диапазон пройден) и `done` (полнота подтверждена). В `checkDone` при
   известном `serverTotals` и `mediaFoundCount() < pictures+videos` — не объявлять `done`: либо
   перезапустить руки на непокрытых диапазонах / финальный gapfill между якорями, либо поставить
   `done` с `reason = «Остановлено: найдено N из M (библиотека не полна)»`.
2. После sparse-терминации руки не останавливаться сразу, а запускать завершающий плотный проход
   (gapfill между соседними якорями направления).
3. Сделать `enqueueSweep` симметричным: весь `DETECT_BLOCK` вокруг `n`, независимо от `dir`.
4. Писать `reason` по рукам (`pos/phase/foundCount/missStreak`) — видно, где рука сдалась.

#### 2. Сброс галереи/предпросмотра при переключении вкладок

Причина. `StateStore.selectSession` (`state-store.ts:187`) при смене вкладки жёстко сбрасывает
`page/files/filesTotal/selection`. Состояние галереи (страница, скролл, сортировка, фильтр, выбор,
размер превью) — общее на все вкладки и не сохраняется per-session. `FilesService` перезагружает
стр. 1 (`files.ts:16-20`), карточки пересоздаются, превью перезапрашиваются.

Как исправить:
1. `Map<string, GalleryUiState>` в `StateStore` (`{page, sort, typeFilter, pageSize, thumbSize,
   selection, scrollTop}`); в `selectSession` — сохранить UI текущей вкладки и восстановить новой
   (сброс до дефолтов только для сессии без сохранённого состояния).
2. Превью: `epoch` в URL уже инвалидирует кэш при сбросе; при переключении вкладок epoch не меняется
   → браузер кеширует. Добавить `trackBy: f.number` в `*ngFor` галереи, чтобы карточки не мигали.
3. Кеш адреса: в `removeSession` (`state-store.ts:173`) удалять запись `GalleryUiState` закрытой
   сессии (и превью-кэш), чтобы не копились объекты удалённых вкладок.

#### 3. Сервер перестаёт отвечать при сканировании нескольких адресов

Причина. Каждая сессия держит свой `Semaphore(C.PROBE_CONCURRENCY=16)` (`scanner.ts:101`), а
`nodeTransport` (`http.ts`) ходит через глобальный `http.Agent` без `keepAlive` и лимита сокетов —
каждый запрос открывает новое соединение. При N сессиях до `16×N` одновременных upstream-сокетов
(≈256 при 16 вкладках) → исчерпание дескрипторов, лимита соединений Twonky, забивание event loop.

Параллельность между сессиями уже есть; проблема — нет глобального потолка и переиспользования
соединений.

Как исправить:
1. Единый глобальный пул соединений: общий `http.Agent`/`https.Agent` с `keepAlive: true`,
   `maxSockets`/`maxFreeSockets` (напр. 64); передавать в `nodeTransport`.
2. Глобальный семафор на все upstream-пробы (общий пул ~32–64) вместо per-session `16×N`, либо
   `min(16, GLOBAL_CAP / активныеСессии)`.
3. Backpressure: не запускать новые пробы при занятости пула, чтобы не копить сокеты.

#### 4. Писать ошибки в логи сервера

Причина. Ошибки глотаются: `fetchServerStats` `catch { return null }` (`server-stats.ts:67`);
scanner `.catch` (`scanner.ts:234,352,670`) только в `reason`; `downloader.downloadItem`
(`downloader.ts:452`) только в `item.error`; thumb `failNeterr` (`routes.ts:339`); `probe` отдаёт
`neterr` с `detail`, но сканер логирует только счётчик `neterrStreak`.

Как исправить:
1. Минимальный логгер (обёртка над `console`): `logError(context, message, err)` с session id / URL.
2. Логировать: сетевые ошибки проб (хотя бы при `NETERR_PAUSE`); сбой скачивания файла
   (`item.error` + номер/URL); ошибки `fetchServerStats`; ошибки записи `state.json` (в `Store`);
   `process.on('unhandledRejection')` + Express error-handling middleware.
3. Не логировать каждый промах (шум) — только переходы состояний и ошибки с контекстом.

#### Дополнительно замечено

- `parseInfoStatus` (`server-stats.ts:23`) ищет ключи `pictures`/`videos`, разбивая по `[\t\n ]+`;
  у разных прошивок формат `info_status` разный (бывают `*_items`/`image_count`). При несовпадении
  `stats=null` и остановка по статистике не работает (безопасно, но проверить реальные ключи).
- `checkStatsDone` сравнивает суммарный `pictures+videos` с суммарным найденным — сам по себе не
  остановит «все фото, не все видео» (верно); реальная остановка — `checkDone`, см. п. 1.
- `downloader.adjust` (`downloader.ts:388`) считает `speedLast` по wall-clock включая паузы — при
  паузе скорость занижается, авто-потоки проседают (косметика).

## 15. Повторный анализ: ошибки и узкие места

### Производительность (главные кандидаты на «сервер перестаёт отвечать»)

1. **Автосейв сериализует весь список находок каждые 5 с.** `snapshot()` (`index.ts:71`) → `scanner.serialize()`
   → `foundList()` (полная сортировка) + `JSON.stringify` всего `found` в `saveNow` (`store.ts:152`).
   При 78k+ находок это десятки МБ JSON и сортировка O(n log n), синхронно блокирующие event loop
   каждые `SAVE_EVERY_MS=5000` (и кратно числу сессий).
   → Сохранять не полный список `found`, а только прогресс скана/очереди (либо дебаунс, либо
     инкрементальная запись, либо увеличенный интервал для больших библиотек).

2. **`foundList()` пересортировывает весь `foundMap` при каждом вызове** (`scanner.ts:190`). Вызывается
   из REST `/files` (каждая страница), `serialize()` (каждый сейв), `downloader.addAll`. Повторный
   O(n log n).
   → Поддерживать отсортированный массив инкрементально (вставка по номеру при `registerFound`) и
     кэшировать; `foundList()` — возврат кэша без сортировки.

3. **`progress()` итерирует весь `foundMap` каждые 500 мс** (SSE `sendScanTick`, `routes.ts:116`) для
   подсчёта `foundImages/foundVideos`. 78k итераций × 2/с × сессий.
   → Инкрементные счётчики images/videos при `registerFound` (уже есть `mediaCounts()` — вынести в поля).

4. **Downloader `takeNext()`/`pendingCount()` — O(n) по всей очереди** (`downloader.ts:379,349`) на каждый
   элемент и в цикле `pump()`/`worker()`. Очередь 78k → O(n²) суммарно (завершённые остаются в `order`
   и сканируются каждый раз).
   → Указатель на первый pending или отдельный список pending; компактно убирать done/skipped из `order`.

### Ошибки корректности

5. **Несоответствие типа `ArmView`.** Серверный `types.ts:117` описывает `ArmView` без `step`/`foundCount`,
   но `scanner.progress()` их возвращает, а клиент (`api.ts:28`) их использует. Выровнять тип на сервере.

6. **Ключи `info_status`.** `parseInfoStatus` (`server-stats.ts:23`) ищет `pictures`/`videos`; у части
   прошивок ключи иные (`image_items`/`video_items`/`image_count` …) → `stats=null`, досрочная остановка
   и причина неполноты не работают. Проверить на живом сервере и/или добавить фолбэк по альтернативным ключам.

7. **Дедуп «уже скачан» только по размеру** (`resolveSaveTarget`, `downloader.ts:56`): разные файлы одного
   размера ошибочно пропускаются. → Сверять content-type/диапазон или добавить режим «не доверять размеру».

8. ~~`sessionDir` = `host_port`~~ — не актуально: Twonky всегда отдаёт `/disk/` (одно и то же содержимое,
   важен только `prefix+номер` в имени файла), а несколько вкладок на один `host:port` не создаются.
   Текущая схема `downloads/<host>_<port>` корректна, фикс не требуется.

9. **Пауза во время первичной разведки теряет прогресс.** `resume()` при `lastDetectStart === null`
   (`scanner.ts:240`) вызывает `beginDetect()`, который делает `visited.clear()` и `probed=0` — разведка
   стартует заново, а не продолжается (находки сохраняются, но пробный прогресс теряется).

10. **Конкурентные записи state.json.** Автосейв и `saveNow` при `shutdown` (`index.ts:141`) могут писать
    один и тот же `*.tmp` одновременно → потеря/повреждение последнего снимка.

11. **`fetchServerStats` вызывается однократно** (при connect и рестарте, `routes.ts:215`, `index.ts:111`) и
    не обновляется — статистика устаревает при долгом скане.

### Мелкие

12. Утечка `uiCache` (`state-store.ts`): при удалении сессии через SSE (`applySessions`) кэш удалённой
    вкладки не чистится.
13. `FilesService.loadPage` (`files.ts:23`) в `finally` безусловно сбрасывает `filesLoading` — при быстрых
    переключениях вкладок более ранний ответ может снять индикатор загрузки у новой.
14. `eps()`/`probeTimestamps` (`scanner.ts`) используют `Array.shift()` (O(n)); массив растёт с
    интенсивностью проб.
15. `downloader.adjust` считает `speedLast` по wall-clock включая паузы.

### Как исправить — реализовано

- **№1/№2 (автосейв + сортировка).** `foundList()` теперь кэширует отсортированный список
  (`sortedFoundCache`), пересобирается только при новых находках; `serialize()`/`/files`/`addAll`
  больше не пересортировывают на каждый вызов. `routes.ts` `/files` копирует массив перед `reverse()`
  (не мутирует кэш). Находки вынесены из `state.json` в append-only `found-<id>.jsonl`
  (`lib/found-log.ts`): `snapshot()` пишет `serializeMeta()` без `found`, находки дописываются по
  `manager.addOnFound`, миграция v2 (found в state.json) → JSONL при старте, лог чистится при
  закрытии вкладки. O(n) stringify на сейв устранён.
- **№3 (progress по всему foundMap).** Инкрементные счётчики `foundImagesCount`/`foundVideosCount`,
  обновляются в `registerFound`/`restore`; `progress()` и `mediaCounts()` читают их за O(1).
- **№4 (O(n²) очередь загрузчика).** `pendingCountValue` (поле) + FIFO `pendingQueue` с указателем
  `pendingHead`; `takeNext()`/`pendingCount()` — O(1). Переходы статуса синхронизированы в `add`,
  `downloadItem`, `retryFailed`, `dropWhere`, `resetQueue`, `restore`.
- **№5 (ArmView).** В `types.ts` добавлены `step`/`foundCount` (совпадает со сканером и клиентом).
- **№6 (ключи info_status).** `parseInfoStatus` пробует алиасы: `pictures/images/image_items/image_count/photos`
  и `videos/video_items/video_count`.
- **№9 (пауза при первичной разведке).** `beginDetect` записывает `lastDetectStart = startNumber`;
  `resume()` продолжает разведку с точки старта, не сбрасывая `visited`/`probed`.
- **№12 (утечка uiCache).** `applySessions` чистит кэш UI сессий, отсутствующих в списке.
- **№13 (гонка filesLoading).** `FilesService.loadPage` использует монотонный `loadSeq`; устаревшие
  ответы не затирают новое состояние и не снимают индикатор.
- **№7 (дедуп по размеру → фингерпринт).** `resolveSaveTarget` получил опциональный `FingerprintCheck`:
  при совпадении размера и наличии сохранённого фингерпринта сверяются хэши первых/последних
  `FINGERPRINT_BYTES` байт; при отличии контента файл перекачивается в суффикс `_N`. Фингерпринт
  сохраняется в sidecar `<file>.fp` после скачивания (локальное чтение краёв файла), удалённый
  фингерпринт берётся Range-запросами (только при наличии сайдкара). Старые файлы без сайдкара —
  фолбэк на размер (обратная совместимость).
